# 权限映射设计:系统 2 权限并入 MIS 角色(v81b 施工;**v83 起升级为四词统一模型 view/add/edit/delete,单表五板块**,本文档三级模型仅存档)

> 2026-08-11 出稿。前置已完成:两套 Users 统一 UI(v77,`meta_user_map` 映射表已建)。
> 本文档解决"规则层":Meta 侧 17 个页面权限怎么在 MIS 的角色体系里表达、live 后怎么桥接。

## 1. 两套模型的差异(现状)

| | MIS | 系统 2 |
|---|---|---|
| 身份 | Supabase profiles + Auth | MySQL users(9 账号) |
| 授权模型 | 角色制:roles → role_permissions(**7 个栏目 × add/edit/delete**) | 账号直挂:**17 个页面 key × edit/view/none** + Superadmin |
| 校验点 | 前端 can() + Supabase RLS can_write() | middleware + requireEdit/requireView |

## 2. 设计:MIS 角色长出「Meta 维度」

**原则:人的身份 = MIS 用户(已定);授权也收口到 MIS 角色。**

- **新表 `role_meta_permissions`**(Supabase):`role_id + meta_key + level(edit/view/none)`,meta_key 照系统 2 的 17 个(brands、business-managers、…、analytics-lifecycle)。不塞进现有 role_permissions(add/edit/delete 三布尔与 level 三级对不上,硬塞会脏)。
- **Roles 编辑抽屉加「Meta 权限」区**:17 key × 三级下拉,和现有 Section 矩阵并排;is_admin 继续绕过一切。
- **前端消费**:Meta 各页面按当前用户角色的 level 渲染——none 隐藏导航项、view 隐藏写按钮(与 v79 的 `allowMetaWrite` 总闸门叠加:总闸门管"全系统能不能写",per-role level 管"这个人能不能写")。
- **默认值建议**:现有 MIS 角色映射——Admin→全 edit;PO→资产 view + rotation/sop edit + 分析 view;PE→全 view(tokens/apps none);USC Team→分析 view,其余 none。(初版,V 可在 Roles 抽屉里随时调。)

## 3. live 桥接(对接清单 F.2 的落实)

- **P1(只读)**:单一 service token,scope 只读——per-role 差异只在 MIS 前端表达,后端无需感知。
- **P2(开写)**:仍单 token;三层防线:①MIS 前端 per-role level;②系统 2 侧 token scope 白名单按批开放写接口(F.1 的节奏);③**审计对人**:MIS 调用时带 `X-MIS-User: <username>` 头,系统 2 action_logs 的 operator 记真实用户而不是服务账号——这需要一个小 patch(往 requireEdit/写路径透传),**列为 P2 patch 清单第一项**。
- **系统 2 的 9 个账号退役路径**:live 后 `/api/users` 拉到真实 9 账号 → 在统一 Users 页逐个映射到 MIS 用户 → P2 桥接上线、审计对人跑顺 → 系统 2 users 表只留 service 账号,其余停用。

## 4. 施工清单(拍板后 1 个版本内)
