## 3. 防反复清单（每条都吵过一轮，结论如下）

1. **后端逻辑复用不重写**——轮转递补规则、权限、审计、collation、时区这些踩坑换来的逻辑留在系统 2 接口里，MIS 只做前端。在 n8n/Supabase 里重写 = 把修好的 bug 重新引入。
2. **Meta/BO 数据不镜像进 Supabase**——去重原则；MIS 经 API 实时取。
3. **决策数据不迁 MySQL（不合库）**——合库是假简化：架构的简单看「改动要动的地方/要懂的东西/要等的人」，不看库的数量。迁过去 = 每次加字段等 Jayden 部署 + 登录绑死 xden 服务器 + 巨量迁移工。
4. **系统 2 的 workflow 不迁实例、不转账号**——credential 跟账号走，移=十来条凭据重接+全量重验证，纯成本零收益；脆弱管线留在最熟的人（Jayden）手里；**公司之后统一 n8n 时按账本一次性整理**。我们新建的 workflow 放 marketing 侧 n8n（adammkt cloud），只「读」事实库、写只写 Supabase。
5. **MIS 保持 cPanel 自主部署**——不搬去任何需要 IT/别人配合的服务器；迭代自由是 MIS 最大的资产（v32→v69 一个月）。
6. **PERFORMANCE 不与 PBI 重复**——品牌层总量看板现阶段仍是 PBI；MIS 本轮只做 PBI 做不了的「花费×成交落到 hypothesis/素材」（ref code join）+ 带 remark 的 Spending 明细。PBI 并入 MIS 是 Vny 的下一阶段。
7. **口径字典已有**，不重做；ref code 体系已有，join 键不用发明。
8. **P1 的 ASSETS 只建三个精选视图**（Health/轮转历史/资产状态）——P1 期间系统 2 UI 还活着，全量只读复刻是过度建设；其余视图 P2 随操作一起建。
