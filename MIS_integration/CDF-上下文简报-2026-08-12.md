## 一、大局：三条线怎么缠在一起的

- **Designer OS / CDF**：V 原计划独立延伸的一条线——Creative Team 所有工作统一进一条 Jira 队列，素材需求自动开票。动手时发现：自动派工的触发源在 MIS，而 MIS 的一半触发数据（广告状态）在系统 2——**所以必须先打通 MIS×系统 2，才能延伸 Designer OS**。
- **三方角色**：
  - **V + code 工作区（Claude）**：MIS 开发；定触发逻辑与数据契约。
  - **Jayden**：系统 2 与 MySQL、生产部署、现有 n8n 的所有者；我们给他代码 patch，他审核部署。**节奏不可控，是最慢的环节。**
  - **Alden**：CDF 执行人。职责=把 MIS 触发接到 Jira ticket + Slack thread + OneDrive folder；workflow 建在 Marketing 的 n8n instance（V 负责邀他进来）。

## 二、MIS 最新架构快照（v85，全部已实现并冒烟通过）

- **五大板块导航**：CI（竞品情报）/ PI（Budget、Idea、Hypotheses、Creatives、Monthly、Dictionary）/ Meta Assets（11 个资产页）/ Analytics（只留 Closed-Loop Report、Spending、Asset Lifecycle；其余下架待 vny 接手数据线）/ Administration（Roles、Budget Permission、Users、Activity Log）。
- **命名契约 v2（V 拍板终版）**：广告名 7 段 `市场_品牌_设定_格式_维度_内容_编号`，例 `USC_OK18_SA_VD_HK_WD_001`，优化重投加 V 后缀（001V2）。编号=3 位流水按品牌×内容全局递增。全维度短码已落库（Supabase dict_entries.short_code）。**唯一性走登记制（方案一）**：素材保存时全名自动登记进 creatives（ads_code/ref_code），闭环归因三层：严格解析→登记全名→品牌。老广告永不改名。
- **实体连接**：广告 ↔ 素材 ↔ 假设 ↔ 验收人（假设负责人）全部靠登记的 ads code 串起来——这正是 CDF 开票字段的数据基础。
- **假设（Hypothesis）**：编号 HYP-###（DB 自动流水）；立项时自带品牌/市场/测试维度/负责人/预计上线/**目标值（成功线）/防守底线**；测试矩阵锁定后自动建素材骨架。
- **素材状态两层映射（刚完成）**：未发布=人工「待上线」；已登记的素材自动对上系统 2 广告状态——审核中/上线中/被拒(红)/已暂停(三种 PAUSED 合并)/有问题；**爆量启发式**（同账户≥3 条同时被拒→标「疑似账户事件」）已内建；账户健康角标（⚠被封/欠款）框架已就位，等真数据源。
- **Budget**：已投放=spending 通道按品牌×月自动汇总（命名 detect 归品，NULL 不计入），Utilization 自动。
- **权限**：四词统一模型 view/add/edit/delete，一张表按五大板块配（role_meta_permissions + role_permissions），PE=PO 默认。
- **工程**：index.html 已拆成 src/ 五块+构建脚本；mock/live 一键切换（MIS_META.mode + token）；35 视图 Playwright 冒烟 + 11 项引擎回归；发版包 v85 已备好（V 定暂不上传 cPanel，改动收尾后一次传）。

**H 节的背景（CDF 的 P0 质量命门）**——我们做过的研究结论：

- Meta 广告 effective_status 是合成状态：ACTIVE/PAUSED/ADSET_PAUSED/CAMPAIGN_PAUSED(层级传导)/PENDING_REVIEW/IN_PROCESS/DISAPPROVED/WITH_ISSUES。**账户不够钱(UNSETTLED)和账户被封(DISABLED)不在广告状态里，在账户级 account_status**。
- 两个 Slack detector channel 六周 862 条 alert 实测：DISAPPROVED 395 条（46%），其中 **46% 是同账户同小时批量翻拒=账户连坐**，不是素材问题。
- 账户级盲区：账户状态每小时同步进系统 2 的 ad_accounts_legacy 表，但**无变更流水、无告警、无 API 出口**；账户被封后其广告状态停止刷新（冻结失真）。生产 9 个采集账户 6 个实际 DISABLED，零告警。
- 已向 Jayden 提三个需求（只锁需求不锁实现）：①账户真实状态可读可知 ②被拒可归因（真拒 vs 连坐）③被拒有原因（ad_review_feedback，designer 才知道改什么）。

## 四、CDF 讨论到目前为止的共识（chat 里接着聊时不必重开的部分）

1. **第一版触发范围**：新 hypo 立项 + 广告被 disapprove。数据好/坏二期另谈——届时注意 MIS 每条假设已自带目标值/防守底线，阈值可逐假设继承，不必发明全局数字（V 认可此思路，细节未谈）。
2. **查重规则（V 确认）**：边沿触发（状态"变成"被拒的瞬间才开票）；同素材+同触发类型+上一张票未关→不重复开；**票关了之后再次被封=新事故开新票**（时间维度天然在内）。
3. **P0 假票防线**：连坐区分做在触发源头（不靠 Creative Team 人工查重兜底）——爆量启发式今天可用，H 节回复后升级账户联查。被拦下的「疑似账户事件」第一版记录但不开 designer 票（skipped），给谁开票待议。
4. **接口方案（V 认可方向）**：MIS 和 Alden 之间垫一张**事件表 cdf_events**（建在 MIS 的 Supabase）——我们负责触发判定并写事件（每行自带开票全部字段：假设号/验收人/品牌/素材编号/ads code/素材图/触发原因/触发时点数据/优先级建议），Alden 只消费这张表开票并回写 ticket 号。理由：不丢票、可对账、查重状态有处落、两边独立演进。
5. **三轨并行（V 已理解并认可框架）**：**Alden 不用等 Jayden**。他开工只需要"票的格式"（契约文档）+ 样品测试事件，不需要触发条件定案；触发条件是 MIS 厨房内部的事，随时可调。Jayden 只卡"被拒侦测器拉真数据"这最后一米，不在 Alden 关键路径上。
6. **纪律两条**：契约 v1 冻结后只加不改；测试事件带 is_test 标记、只进沙盒 Jira 项目。
7. **Jira ticket 挂 MIS 键**（V 认可）：label 带假设号+素材编号/ads code → 查重一句 JQL、MIS 可反向显示 ticket 状态、后续可统计返工率。
